# Base de audit log

`Usuarios.AuditEvent` conserva fecha, actor nullable, acción, tipo/id de recurso, UUID de solicitud generado por servidor y resultado. No incluye contraseñas, cookies, tokens, payload ni clínica; se añade `X-Request-ID` a respuestas. El admin permite consulta a quienes tengan permiso Django y bloquea alta/cambio/borrado desde interfaz; usuarios normales no tienen endpoint para modificar eventos. La base y sus administradores aún pueden alterar registros: no es WORM ni prueba de integridad independiente. Definir retención, custodia y exportación protegida con seguridad/legal.

Se registran login correcto/fallido y logout, lectura/edición de paciente en API, actualización de antecedentes/odontograma, carga/borrado/descarga de imagen, análisis exitoso, consulta/actualización de consentimiento y exportaciones; también algunas lecturas y escrituras tradicionales. Solo se registra éxito ante respuesta 2xx y actor autenticado; rechazos no se describen como éxito. Las mutaciones API seleccionadas y evento se ejecutan bajo `transaction.atomic`; la inferencia no mantiene una transacción larga y el evento actual refleja éxito, no cada solicitud/fallo. Algunas rutas HTML devuelven redirecciones y aún no están cubiertas por eventos de escritura; ampliar instrumentación explícita antes de considerar auditoría integral. No hay versiones anteriores, registro de lecturas exhaustivo, ni garantía de integridad frente a DB admin. SEC-010 permanece **PARTIALLY RESOLVED**. Datos y storage no forman una transacción única.
