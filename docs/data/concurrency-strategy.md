# Concurrencia

Antes, `get_or_create` sin unicidad podía crear dos antecedentes/odontogramas y PUT sobrescribía el último cambio. Ahora cada escritura de esos recursos bloquea la fila del paciente con `select_for_update` dentro de una transacción, revisa duplicados y compara `version` suministrada por el cliente. Una versión obsoleta devuelve 409 sin cambiar estado, revisión ni audit event. La primera versión es 0; guardar produce 1. GET no crea filas. Se requiere la versión también en HTML; clientes API anteriores deben actualizarse. SQLite no demuestra bloqueo.

Citas bloquean la fila al actualizar o cambiar de estado y comprueban transición tras adquirir el lock; PATCH preserva los campos omitidos. No hay control optimista para el resto de datos de cita. Se conserva el bloqueo de refresh JWT existente. Dos transiciones de distinto destino no pueden aplicarse ambas después de la primera; repetir el destino es idempotente.

La prueba `api/tests/test_postgres_concurrency.py` crea base PostgreSQL de nombre aleatorio mediante `SmileManager.settings_postgres_test` y ejecuta dos escrituras simultáneas sobre un expediente sin antecedentes: una gana y otra recibe conflicto; se comprueba una fila y una revisión. Otra prueba enfrenta completar y cancelar una cita: una transición gana y la otra devuelve conflicto. Ambas pasaron sobre PostgreSQL con base temporal creada y eliminada por Django. `run_phase2_postgres_tests.py` toma la configuración local del contenedor de desarrollo sin imprimir credenciales; el settings de prueba exige conexión de mantenimiento a `postgres` y crea un nombre aleatorio de test. **POSTGRESQL VERIFICATION REQUIRED** para carreras en consentimiento, estudio, IA y operaciones ajenas a este servicio; no existe garantía de que una escritura administrativa directa respete los locks.
