# Evidencia E2E

**Cierre:** Playwright crea un directorio `.e2e-run-*` único para cada ejecución y pasa su ruta explícitamente al servidor; solo limpia ese directorio y el proceso que creó. No borra `.e2e.sqlite3` ni `.e2e-media` preexistentes. El puerto loopback se comprueba libre antes de iniciar; no debe utilizarse un servidor externo. En la suite de paridad los límites de throttle se incrementan únicamente para evitar interferencia entre escenarios largos; las pruebas específicas de throttle conservan sus límites propios.

El recorrido principal UI (`core-flow.spec.js`, ejecución individual) pasó con datos sintéticos: login, dashboard, alta/edición de paciente, expediente, antecedentes, odontograma, consulta, imagen, análisis IA en UI, consentimiento, exportaciones, cita y logout. El historial de ejecuciones IA no se expone en UI: **NOT COVERED UI**; se prueba vía HTTP en `production-readiness.spec.js`. La ejecución cruzada HTTP previa cubre los recursos detallados abajo; la interfaz comprueba rechazo de paciente ajeno. No se afirma una variante de navegador con PostgreSQL ni UX de 409/413/429 completas. Una primera ejecución conjunta falló por throttling compartido; otra detectó una aserción obsoleta de paginación, corregida antes del pase individual.

`production-readiness.spec.js` se volvió a ejecutar individualmente y pasó con inferencia HTTP real, BOLA e inspección del build: navegar a `/app/design-system` redirige a la aplicación y no muestra el laboratorio. El recorrido UI y esta prueba pasaron en ejecuciones separadas; la suite conjunta completa no se volvió a ejecutar tras corregir la aserción. Las pruebas del recorrido UI incluyen respuestas simuladas para varios errores antes de repetir las acciones reales; no demuestran de extremo a extremo todos los códigos 409/413/429.

La prueba de navegador de readiness usa SQLite y media sintéticos aislados mediante `SmileManager.settings_e2e`; no representa PostgreSQL ni S3 de producción. La suite legacy previa incluía una ruta a un archivo bajo `media/`; fue sustituida por una imagen sintética para evitar utilizar datos existentes. La ejecución individual posterior del recorrido principal y el alcance cubierto se describen arriba.

Históricamente el setup E2E usaba rutas fijas `.e2e.sqlite3` y `.e2e-media`; el setup actual utiliza el directorio único indicado arriba. El análisis IA de la prueba de readiness inferior se ejecutó por HTTP; el recorrido UI posterior también lo ejecuta mediante interfaz.

Los tests Django cubren propiedad, CSRF, JWT, revisión clínica, imágenes y fallos de storage con DB y media temporales. Esos resultados no sustituyen pruebas dinámicas de navegador, TLS, S3 o proxy.
