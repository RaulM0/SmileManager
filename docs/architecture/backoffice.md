# Backoffice de SmileManager

`/backoffice` es una interfaz operativa separada de la aplicación clínica. La API versionada `/api/v1/backoffice/` verifica la capacidad de producto en cada petición. Desde la ampliación actual, esa capacidad permite consultar globalmente pacientes y secciones clínicas específicas mediante endpoints auditados de solo lectura; no permite escritura clínica. Este cambio amplía los privilegios de asignaciones existentes y requiere revisión antes de producción. Django Admin permanece como herramienta técnica: las entidades clínicas registradas son de solo lectura; AuditEvent es de solo lectura y ClinicalRevision/AIAnalysisRun no están expuestos.

El permiso Django `Usuarios.access_system_backoffice` se asigna expresamente a usuarios o grupos fuera del panel. `is_staff` no lo concede y un superusuario técnico tampoco lo recibe automáticamente: la policy comprueba asignación directa o por grupo. No se crean cuentas ni se otorgan permisos desde el panel. La migración crea el permiso a través del ciclo normal de Django; no asigna administradores automáticamente. La asignación inicial y su custodia deben realizarse por un operador técnico autorizado.

Endpoints: `dashboard/`, `users/`, `users/{id}/`, `users/{id}/activate/`, `users/{id}/deactivate/`, `audit/`, `audit/{id}/`, `ai-runs/`, `ai-runs/{id}/`, `system/`. Listas paginadas por servidor (20, máximo 100); filtros en servidor. Usuarios solo permite activación/desactivación; rechaza cualquier cambio de estado para la propia cuenta, staff, superusuarios o usuarios con asignación de backoffice. Se trata de una política conservadora para proteger administradores, no de un modelo de roles clínicos. Las cuentas privilegiadas se administran mediante un proceso técnico separado.

Los cambios se ejecutan con bloqueo y transacción, registran `USER_ACTIVATED` o `USER_DEACTIVATED` sin payload, y la desactivación pone en lista negra los refresh vigentes. Access tokens existentes se comprueban contra `is_active`; el diseño JWT no proporciona revocación instantánea independiente del estado, por lo que reactivación y carreras de sesión deben valorarse operativamente. No se guardan contraseñas ni tokens en auditoría. La policy evita que el último administrador operativo sea desactivado desde esta superficie; no protege contra cambios de permisos directos simultáneos mediante ORM/admin técnico.

Auditoría y ejecuciones IA exponen solo metadatos. El hash de entrada, detecciones, archivos y datos clínicos no se exponen. `potentially_stale` es orientativo con umbral `BACKOFFICE_AI_STALE_SECONDS` (3600 s por defecto), no recupera ni cambia la ejecución. Recuperación requiere el procedimiento operacional existente. La readiness comprueba DB y no ejecuta IA. No hay WORM: DBA y shell quedan fuera de la frontera de aplicación.

Las secciones clínicas dedicadas sí exponen datos clínicos y snapshots de revisión. Véase [acceso a datos](../security/backoffice-data-access.md). El listado de imágenes no proporciona archivos ni enlaces directos.

Futuro: `User → Membership → Clinic → Role → Resource` requiere decisiones de negocio y una nueva policy detrás de las interfaces de autorización; no se agregaron tablas de clínica ni roles.
