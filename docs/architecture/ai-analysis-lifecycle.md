# Ejecuciones de análisis IA

`AIAnalysisRun` conserva imagen, referencia técnica, actor, fechas, estado RUNNING/SUCCEEDED/FAILED, SHA-256 del artefacto y entrada, resultado en storage, detecciones estructuradas, categoría genérica de fallo, UUID de solicitud y bandera de reanálisis. La inferencia sigue síncrona: RUNNING es estado observable, no una cola. La versión se consulta por HTTP en SmileIA y se exige al solicitar la inferencia; el artefacto vive en ese proyecto independiente y debe permanecer inmutable durante la vida del proceso. Un cambio de pesos requiere reiniciar SmileIA. El hash no es autorización ni se incluye en el endpoint público de historial.

Tras verificar propietario, se calcula huella de entrada. Bajo bloqueo DB de la imagen se busca ejecución activa; si existe, se devuelve 202 `running` y no se duplica inferencia. Existe constraint parcial de una ejecución RUNNING por imagen. Sin `force`, se reutiliza el último resultado exitoso con igual imagen, hash de entrada, modelo y referencia actual si el objeto existe. `force=true` solicita nueva ejecución; un UUID `Idempotency-Key` conserva la intención de reanálisis para reintentos con esa misma clave y rechaza clave reutilizada para otro input/modelo. El cliente genera una clave por acción y la conserva durante el retry automático de la petición. El reintento posterior a un fallo con la misma clave devuelve conflicto; iniciar nueva intención requiere otra clave. Una solicitud `force` mientras hay un trabajo activo recibe `running` y debe repetirse después. Un nuevo click genera otra intención.

`GET clinical-images/{id}/analysis-runs/` pagina metadatos; `GET clinical-images/{id}/analysis-runs/{run_id}/file/` entrega resultado autorizado. Los permisos se heredan de la imagen filtrada por propietario; no se usa el hash como llave de acceso. AuditEvent registra solicitud, reutilización, reanálisis y fallo sin detecciones. Datos clínicos y hashes requieren protección de DB y backup. El historial anterior a la migración no se inventa. La eliminación de imagen deja run con FK nula y referencia técnica; **LEGAL/CLINICAL DECISION REQUIRED** para retención y trazabilidad del actor borrado.

Limitaciones: caída de proceso puede dejar RUNNING indefinido; se necesita detección/reconciliación operativa antes de habilitar retries automáticos, pues no hay worker durable. Fallo previo al cálculo de hash puede no crear run. La escritura del archivo resultado y DB no es atómica; un fallo puede dejar objetos huérfanos o una referencia actual sin run exitoso. El timeout HTTP no cancela el trabajo remoto en SmileIA. Una rotación o reemplazo de imagen fuera de las rutas controladas puede requerir reconciliación. Revisar backup, migración y despliegue antes de producción. **PARTIALLY RESOLVED** para durabilidad e idempotencia de punta a punta.

## Ruta multitenant

`POST clinics/clinical-images/{id}/analyze/` exige contexto y asignación profesional vigentes; historial y descargas se encuentran bajo `analysis-runs/` de esa imagen. La inferencia genera el resultado temporal sin modificar el expediente. Antes de publicarlo, el servicio bloquea clínica, usuario, paciente e imagen, vuelve a comprobar autorización y procedencia y verifica que el run siga RUNNING y la imagen no haya cambiado. Si se revoca la membresía o se suspende la clínica durante la inferencia, no se publica el resultado. Una recuperación previa no es sobrescrita por una inferencia tardía. La reutilización e idempotencia se limitan a la imagen y clínica autorizadas.

La escritura al storage ocurre durante la transacción de publicación; una excepción provoca limpieza compensatoria del objeto nuevo cuando es posible. DB y storage siguen sin compartir una transacción distribuida: una caída del proceso o un fallo de limpieza puede dejar un objeto huérfano, por lo que sigue siendo necesaria la reconciliación operativa. La inferencia no mantiene bloqueos de DB, pero la publicación sí puede esperar a storage. Estas garantías no sustituyen la validación general de aislamiento ni las pruebas E2E de toda la aplicación.

## Recuperación operativa

`manage.py recover_stale_ai_runs --older-than-minutes N --clinic-id UUID` inspecciona esa clínica sin escribir y muestra únicamente identificador y edad. Una operación global requiere `--all-clinics` explícito e incluye ejecuciones históricas sin clínica. El umbral N es una decisión operativa y debe superar la duración legítima máxima observada. Para aplicar, primero detener y verificar externamente **todos** los procesos capaces de ejecutar inferencia; después usar `--apply --workers-stopped`. El comando no puede comprobar esa declaración. Si se aplica mientras una inferencia aún está activa, esta puede escribir su resultado y sobrescribir el estado recuperado: **no es seguro aplicarlo con workers vivos**. Los candidatos aún RUNNING y antiguos se marcan FAILED / `process_interrupted` mediante transacción y evento de auditoría; no se lanza inferencia. Registrar por separado la identidad del operador en la plataforma de operaciones, pues el evento técnico no autentica al ejecutor del comando. Una clave idempotente ya utilizada sigue asociada al run fallido: una nueva intención requiere otra clave. Reconciliar almacenamiento antes de reiniciar workers.
